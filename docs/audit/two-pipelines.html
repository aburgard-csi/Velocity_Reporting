How his works

The build is in the middle of the picture, not at the end of it. Everything to the left tells him what arrived, everything to the right tells him what shipped, and the changelog closes the loop back into the next build.

  • Inputs. One environment variable names the data root. The daily watcher diffs the CSI shares and the Outlook mailbox against the inventory it saved last time, then files each new file into a folder per kind. He treats the original sources as the backup and keeps no mirror.
  • Build. Four per-program builders, each behind its own subagent, each starting from a stripped template shell. A combined deck is assembled from the individual decks, never blended.
  • Gate. Unit suite, then the deck validator, then a layout-fingerprint diff against a baseline, then a package-integrity check. A non-zero exit blocks delivery and the fix goes in the builder.
  • After the build. Decks are filed by CSM. A dashboard shows readiness per client and records "sent" from a button, because nothing on disk knows whether a deck reached the client. A performance page across all clients is refreshed daily and republished only when its content hash changes.

How yours works

Yours is a wider engine with the same left-to-right shape, but the loop after the build is thinner. The strength is in the middle: the depth of analysis and the size of the test suite around it.

  • Inputs. The fetch script already does something his does not: it discovers each CSM's month folder however they spelled it. But it runs on demand, keeps no inventory, and cannot tell you a file was re-landed with new bytes.
  • Engine. This is where you are far ahead. The ODD analysis, transaction intelligence, deposits, market and competition, ILS, and CashPlease engines have no counterpart in his repo.
  • Checks. You have more kinds of check than he does: a config validator, an extract-shape check, a post-run checklist, a form audit, copy-rule enforcement, and guard tests for month literals, drive letters, doc drift, and privacy. They are not chained into one gate, and none blocks delivery with an exit code.
  • After the build. Output lands in 03-Output. The receipts model is designed and the folder is empty. The delivery board is specified in a design doc and not built.

The iterative loop: his practices

These are the habits that make his product better after each review cycle. They are not clever code. They are rules about what happens when something goes wrong, and each one traces to a specific shipped defect. The badge on each card says whether v5 already has it.

The one that matters most. Standing rule, Aaron, 2026-08-17: when a defect gets through the gate, add the check that would have caught it. Fixing only the instance guarantees the next one ships too. Everything else on this page is scaffolding around that sentence.

01

Defect becomes rule

The validator docstring lists every rule beside the defect it exists for: reference leak ("Union Financial" on a Q&A slide), closing-month mismatch (2026.09 ARS decks), table label fit (branch names, yesterday). The file is a history of what got through.

validation/validate_deck.py, CLAUDE.md "Standing rule"

v5: partial You have render-guard tests but no rule ledger and no single gate they feed.
02

Changelog with an inclusion rule

Anything that changes a number, its source, what a slide claims, or what it renders. Newest first, dated, with the reason. A correction entry names the affected decks, the fix, the check that would have caught it, and the test. 166 entries in three weeks.

CHANGELOG.md, entry 2026-09-16 "Reg E opt-in read as zero"

v5: no Records, specs, handoffs, and REFERENCE exist, but no ledger of what moved a number.
03

Fix the builder, never the deck

A layout or number defect is fixed in the builder, the geometry contract, or the template shell, then rebuilt. Editing a delivered deck fixes one client and leaves the rest broken.

README.md, CLAUDE.md "Templates"

04

Build from the shell, never clone

A deck cloned from another client's carries that client's numbers, captions, and notes forward, and a figure that was never swapped looks identical to one that was. So the gate has to hunt for leaks, and the rule exists to make that rare.

"(Aaron, 2026-09-14)" sits on the rule itself, in the file the agent reads. Reversals go into a table and the old decision stays visible. A future session cannot re-litigate what was settled, and cannot mistake an old rule for a current one.

Your config validator, your privacy boundary with a test behind it, your MCP surface, your ILS and transaction engines, and your Client-Master-driven roster have no counterpart in his repo.
